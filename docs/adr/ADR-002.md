# ADR-002: Arquitectura híbrida de Backend con Firebase (Auth, Firestore y Security Rules) y Supabase (Almacenamiento de imágenes)

- **Estado:** Aprobado
- **Fecha:** 2026-11-21
- **Autor(es) y equipo:** Díaz Bedón Daniel Andrés (Proponente) — Equipo Grupo 5: Díaz Bedón Daniel Andrés, Lucero San Lucas Jimy Sullivan, Vargas Chávez Michael Jordan
- **Requisitos relacionados:** Punto 1 (autenticación, control de acceso por roles, persistencia de datos e imágenes), R1 (precarga de recintos, 5 organizaciones y candidatos), R2 (jerarquía sin autorregistro y confirmación), R3 (login con cédula, clave inicial `Ecuador2026`, cambio obligatorio en primer acceso y recuperación por correo, sin claves admin en la app), R4–R6 (gestión provincial, de recinto y registro de actas), R7 (almacenamiento de fotos de actas y GPS), R8 (reglas de seguridad en backend por rol y pertenencia).

## Contexto

La aplicación requiere una solución backend gratuita que soporte:
1. Autenticación controlada sin autorregistro abierto, permitiendo que el Coordinador Provincial cree Coordinadores de Recinto y estos creen Veedores (R2), con inicio de sesión mediante cédula ecuatoriana, contraseña inicial `Ecuador2026`, cambio obligatorio en el primer ingreso y recuperación por correo (R3).
2. Persistencia estructurada y en tiempo real de provincia, cantón, parroquia, recintos, JRV, cinco organizaciones políticas, candidaturas de alcaldía/prefectura, actas y coordenadas GPS (R1, R4–R7).
3. Reglas de seguridad en el servidor que impidan que un veedor consulte o modifique JRV o actas ajenas (R8).
4. Almacenamiento gratuito y confiable para las fotografías de cada acta (R7) sin exigir tarjeta de crédito.

## Alternativas consideradas

| Alternativa | Ventajas para este caso | Desventajas / riesgos |
| :--- | :--- | :--- |
| **Opción A: Arquitectura híbrida Firebase (Authentication + Cloud Firestore + Security Rules) + Supabase (Storage para imágenes)** | Firebase Auth provee gestión robusta de identidad, recuperación de contraseña por correo (R3) y creación administrativa mediante instancia secundaria sin cerrar sesión ni exponer claves admin; Firestore ofrece sincronización en tiempo real para el dashboard provincial (R4) y Security Rules granulares por rol y JRV asignada (R8); Supabase Storage aporta 1 GB gratuito sin tarjeta de crédito para guardar las fotos de las actas (R7) mediante buckets con políticas de acceso. | Requiere vincular el identificador del acta/usuario de Firebase con la ruta del archivo en Supabase Storage y mantener dos SDKs (`@angular/fire` y `@supabase/supabase-js`). |
| **Opción B: Únicamente Firebase (Auth + Firestore + Firebase Storage)** | Un solo ecosistema y un único SDK en toda la aplicación. | En proyectos nuevos, habilitar Firebase Storage en el plan Spark exige asociar una cuenta de facturación (plan Blaze con tarjeta de crédito), lo que representa un riesgo operativo para el equipo. |
| **Opción C: Únicamente Supabase (Auth + PostgreSQL + Storage)** | Base de datos relacional PostgreSQL y almacenamiento integrados en una sola consola. | Los proyectos gratuitos de Supabase se pausan automáticamente tras 7 días de inactividad y el alta jerárquica de usuarios sin autorregistro desde el cliente requiere Edge Functions para no exponer la clave `service_role` (R3). |
| **Opción D: PocketBase (Binario único Go + SQLite WAL + Auth + Storage + API Rules)** | 100% gratuito y código abierto (licencia MIT), sin límites de usuarios activos ni suspensión automática por inactividad; colecciones auth con desactivación de autorregistro (`CreateRule` restringida a roles superiores), soporte para campo `cedula` como identificador de login, flujo SMTP nativo para confirmación de cuenta (R2) y recuperación de clave (R3), y campo booleano `debe_cambiar_clave`; motor de API Rules en servidor (`@request.auth.rol` y pertenencia `@request.auth.id = jrv.veedor`) que bloquea acceso a mesas ajenas (R8); almacenamiento de fotos de actas integrado con tokens protegidos y SDK TypeScript ligero (~40 KB). | Requiere desplegar el ejecutable en un contenedor/VPS gratuito (ej. Fly.io, Render o Oracle Cloud Always Free) con volumen persistente montado (`/pb_data`) para conservar SQLite e imágenes ante reinicios; SQLite admite un escritor concurrente a la vez (mitigado con modo WAL). |

## Decisión

Se adopta una arquitectura híbrida utilizando Firebase (Firebase Authentication + Cloud Firestore + Firestore Security Rules) para autenticación, datos electorales y autorización por rol/pertenencia, junto con Supabase Storage como repositorio dedicado para almacenar las fotografías de las actas (bucket `actas-evidencias`). Para la creación jerárquica de cuentas (R2) sin cerrar la sesión del coordinador activo ni incluir credenciales privilegiadas en la app (R3), se emplea una instancia secundaria de Firebase App.

## Consecuencias

- **Beneficios:** Costo $0 sin requerir tarjeta de crédito, actualización en tiempo real del consolidado provincial (R4), flujo nativo de recuperación de contraseña por correo (R3) y almacenamiento dedicado en Supabase Storage para evidencias fotográficas (R7).
- **Obligaciones:** Definir Firestore Security Rules verificando `request.auth.uid`, `rol` y pertenencia a recinto/JRV, y configurar políticas RLS en Supabase Storage.
- **Limitaciones y riesgo:** Podría ocurrir inconsistencia si se guarda el acta en Firestore pero falla la subida de la foto a Supabase; se mitiga ejecutando primero la carga de imagen en Supabase Storage y registrando el documento en Firestore únicamente tras obtener la URL válida.

## Verificación

Prueba de seguridad desde la app y consola autenticando como `veedor_1` (asignado a `JRV-01`) e intentando leer o editar `JRV-02`: Firestore Security Rules debe rechazar la operación (`permission-denied`). Comprobar creación jerárquica de usuarios, cambio obligatorio de clave `Ecuador2026`, subida de foto al bucket de Supabase Storage y almacenamiento de su URL y GPS en Firestore.
